# agent007 — Design Spec
**Date:** 2026-03-16
**Status:** Draft v8

---

## Overview

agent007 is a multi-agent AI orchestration framework written entirely in Rust. It is inspired by Ruflo (formerly claude-flow) and Claude Code, combining:

- Multi-agent swarm orchestration (like Ruflo)
- A skills system, hooks, MCP support, and persistent memory (like Claude Code)
- Native support for Claude, Codex, and Ollama (local open-source models)
- RAG-powered memory using LanceDB
- IDE integration for Zed, VSCode, and JetBrains
- A TUI dashboard (phase 1) and Web UI (phase 2)
- Self-learning via RL-style reward signals (phase 1) and full RL fine-tuning via Ollama (phase 3)
- Code zone protection (safe/unsafe file regions), custom workflow DSL, git-aware agents, checkpoint/rollback, debug loop, human-in-the-loop gates, token/cost budget guard, agent persona library, audit log, code impact analysis, parallel orchestration, session replay (phase 2)
- Testing agent pipeline (strategist, designer, writer, runner, regression tracker) (phase 2)
- Simulation agent pipeline with domain-specific templates (WiFi RTT, WiFi roaming, custom) and research integration (phase 2)

The system starts local-first but is designed for distributed operation later.

---

## Goals

- Orchestrate multiple AI agents to complete complex tasks collaboratively
- Support multiple model backends: Claude (Anthropic), Codex (OpenAI), Ollama (local)
- Provide a Claude Code-style skills system for reusable agent workflows
- Integrate directly into Zed, VSCode, and JetBrains via LSP/extensions
- Store and retrieve context using RAG-powered persistent memory
- Fire event hooks before/after agent actions
- Connect to external tools via MCP protocol
- Expose a rich TUI dashboard and (phase 2) a browser-based Web UI

---

## Non-Goals (v1)

- Cloud deployment / horizontal scaling (designed for later, not v1)
- Web UI (phase 2)
- Custom model fine-tuning for Claude or Codex (API-only, not supported)
- Phase 3 Ollama fine-tuning via external tools is in scope (see Self-Learning, Phase 3)
- Mobile support

## Error Handling Policy

**Rule: `thiserror` for all library crates; `anyhow` only in the `cli` binary.**

- Every crate in `crates/` (except `cli`) defines typed error enums with `thiserror`. Public APIs return `Result<T, CrateError>`.
- The `cli` crate uses `anyhow` to wrap all library errors with context for human-readable output.
- Library crates must **never** expose `anyhow::Error` in their public API signatures. This keeps crate boundaries clean and composable.

---

## Async Trait Policy

Rust 1.75+ supports async functions in traits natively (RPITIT). However, RPITIT-based async traits are not object-safe by default, which means `Box<dyn ModelProvider>` won't compile without extra work.

**Rule:** Use `async-trait = "0.1"` on all public traits that must be used as trait objects (e.g., `ModelProvider`, `EmbeddingProvider`, `VectorDB`, `Dispatcher`). Use native async fn in traits only for concrete types or when trait objects are not needed.

This policy must be consistent across all crates. Mixing `async-trait` and native async fn on the same trait definition will cause incompatible implementations.

---

## Testing Strategy

- **Unit tests:** Each crate has `#[cfg(test)]` modules. Async tests use `#[tokio::test]`.
- **Mocking:** `ModelProvider` and `EmbeddingProvider` traits have hand-written `MockProvider` implementations (no `mockall` crate — see Key Dependencies for rationale) for use in tests that must not make real API calls.
- **Integration tests:** Each crate has a `tests/` directory. The `core` crate integration tests exercise the full agent lifecycle with mock providers.
- **MCP tests:** The `mcp` crate tests against a local `rmcp` test server to avoid `npx` subprocess dependency in CI.
- **No real API calls in tests:** Tests must never call real Claude/Codex/Ollama endpoints. All external calls are mocked via `MockProvider`.

## Agent Engine (core)

### Agent Types

- **Orchestrator Agent** — receives the user task, decomposes into subtasks, assigns to workers
- **Worker Agents** — specialized (Architect, Coder, Reviewer, Researcher, etc.), each runs a model
- **Tool Executor** — handles tool calls (bash, file I/O, web search, MCP tools)

### Concurrency Model

- Each agent runs as a `tokio::task` (green thread, not OS thread).
- Maximum concurrent agents is configurable (`config.toml: core.max_agents`, default 8).
- The task queue uses `tokio::sync::mpsc` channels (not `broadcast`) — one sender per producer, one receiver per agent. This avoids dropped messages under backpressure.
- Backpressure: the task queue channel has a bounded capacity (default 256). The orchestrator waits when the queue is full rather than spawning unbounded tasks.

### Event Bus

The event bus uses a `Dispatcher` trait so Phase 3 can swap in a network transport without touching agent logic. The `subscribe` method returns a `Pin<Box<dyn Stream<Item = AgentEvent> + Send>>` — not a concrete `broadcast::Receiver` — so the trait remains swappable across Phase 1 (local) and Phase 3 (network) implementations:

```rust
use futures::Stream;
use std::pin::Pin;

#[async_trait]
pub trait Dispatcher: Send + Sync {
    async fn publish(&self, event: AgentEvent) -> Result<(), CoreError>;
    async fn subscribe(&self) -> Result<Pin<Box<dyn Stream<Item = AgentEvent> + Send>>, CoreError>;
}

// Phase 1: LocalDispatcher (wraps tokio::broadcast, capacity 1024, returns stream adapter)
// Phase 3: NetworkDispatcher (libp2p or gRPC, same interface)
```

### AgentEvent — Data Handling

Events on the bus must never carry raw prompt text (which may contain API keys or sensitive user data). The `ModelRequest` variant carries a `PromptRef` (an opaque ID referencing prompt content stored in a secured in-memory store), not the raw string. The TUI and hooks system receive only the `PromptRef` and resolved metadata (agent id, model name, token count).

No raw sensitive content (prompts, memory values) is carried on the bus. Both `ModelRequest` and `MemoryWrite` use opaque ref handles:

```rust
pub enum AgentEvent {
    TaskAssigned { agent_id: AgentId, task: Task },
    TaskCompleted { agent_id: AgentId, result: TaskResult },
    ToolCall { agent_id: AgentId, tool: ToolCall },
    MemoryWrite { key: String, value_ref: MemoryRef },  // opaque ref, not raw value
    HookFired { event: HookEvent },
    ModelRequest { provider: String, prompt_ref: PromptRef, token_estimate: usize },
}

pub struct MemoryRef(pub Uuid);  // opaque handle into MemoryStore
pub struct PromptRef(pub Uuid);  // opaque handle into PromptStore
```

### Core Types (sketch)

```rust
pub struct AgentId(pub Uuid);
pub struct Task { pub id: Uuid, pub description: String, pub assigned_to: Option<AgentId> }
pub struct TaskResult { pub task_id: Uuid, pub output: String, pub success: bool }
pub struct ToolCall { pub name: String, pub args: serde_json::Value }
pub struct PromptRef(pub Uuid); // opaque handle into PromptStore
```

### Agent Cancellation and Shutdown

All agent tasks are spawned into a `tokio_util::task::TaskTracker` (from `tokio-util`). On shutdown (TUI `q`, SIGINT, or SIGTERM):

1. A `CancellationToken` (from `tokio-util`) is cancelled.
2. All agents observe the token and exit their work loops cleanly.
3. The `TaskTracker::wait()` ensures all tasks complete before the process exits.
4. In-progress results are flushed to the memory store before shutdown.

This ensures no dangling tokio tasks and no partial writes to the vector DB.

### SubOrchestrator Trait

Hierarchical sub-orchestrators are defined in `custom-agents` and implement the `SubOrchestrator` trait declared in `core`. This keeps the dependency direction clean: `custom-agents → core`, never the reverse.

```rust
// In core crate — trait definition only
#[async_trait]
pub trait SubOrchestrator: Send + Sync {
    /// Human-readable name (e.g., "LibP2PSubOrchestrator")
    fn name(&self) -> &str;

    /// File paths this sub-orchestrator owns (scopes RAG context)
    fn scope(&self) -> &[String];

    /// Decompose an incoming task into subtasks and execute them.
    /// Returns a structured result to the parent orchestrator.
    async fn execute(&self, task: Task) -> Result<SubTaskResult, CoreError>;
}

pub struct SubTaskResult {
    pub task_id: Uuid,
    pub output: String,
    pub files_changed: Vec<PathBuf>,
    pub tests_written: usize,
    pub tests_passing: usize,
    pub coverage_delta: Option<f32>,
    pub unresolved_blockers: Vec<String>,
}
```

Dependency direction: `custom-agents` implements `SubOrchestrator` from `core`. `core` never imports `custom-agents`. The `cli` crate wires them together at startup, registering each loaded `SubOrchestrator` with the top-level `Orchestrator`.

### Worker Result Routing

Worker agents return results to the Orchestrator via a dedicated `tokio::sync::mpsc` **response channel** — one per spawned worker, created by the Orchestrator at dispatch time:

```
Orchestrator
    │
    ├── creates (task_tx, task_rx) per worker
    ├── sends Task via task_tx
    └── awaits TaskResult via result_rx
              │
        Worker Agent
              │
              └── sends TaskResult via result_tx
```

The response channel is separate from the event bus. The event bus is for observability (TUI, hooks, IDE). The response channel is for control flow (Orchestrator waiting on worker output).

### Task Flow

```
User task
    │
    ▼
Orchestrator Agent       ← breaks task into subtasks
    │
    ├──> Architect Agent  (claude)
    ├──> Coder Agent      (codex / ollama)
    └──> Reviewer Agent   (claude)
              │
              ▼
         Tool calls       ← hooks fire before/after
         MCP servers
         Shell commands
              │
              ▼
         Memory Store     ← results written back + indexed
              │
              ▼
         TUI / IDE / Web  ← user sees live updates
```

    async fn complete(&self, request: CompletionRequest) -> Result<CompletionResponse, ModelError>;

### Implementations

- `ClaudeProvider` — Anthropic API (best reasoning, code review)
- `CodexProvider` — OpenAI API (best for code completion)
- `OllamaProvider` — local REST API (OpenAI-compatible), any open-source model (llama3, mistral, gemma, etc.)
- `MockProvider` — test double, returns configurable canned responses

### Model Router

Routes tasks to the most appropriate model based on config rules:

```toml
[models.routing]
code_completion = "codex"
reasoning = "claude"
fast_local = "ollama"
sensitive = "ollama"       # never leaves machine
default = "claude"
```

### Memory Namespacing

```rust
// In memory crate
pub struct ScopedMemoryStore {
    inner: Arc<MemoryStore>,
    namespace: String,  // e.g., "libp2p", "auth", ""  (empty = global)
}

impl ScopedMemoryStore {
    /// All reads/writes are prefixed with the namespace.
    /// Markdown files: ~/.agent007/memory/<namespace>/user.md
    /// LanceDB rows: keyed as "<namespace>/<key>"
    pub fn read(&self, key: &str) -> Result<Option<String>, MemoryError>;
    pub fn write(&self, key: &str, value: &str) -> Result<(), MemoryError>;
}

impl MemoryStore {
    pub fn scoped(&self, namespace: &str) -> ScopedMemoryStore;
    pub fn global(&self) -> ScopedMemoryStore { self.scoped("") }
}
```

The top-level orchestrator uses `store.global()`. Sub-orchestrators use `store.scoped("libp2p")`. The RAG index is global (all namespaces contribute to it) but retrieval can be filtered by namespace via metadata in the vector payload.

## Skills System (skills crate)

Skills are reusable prompt workflows stored as markdown files with YAML frontmatter.

### Skill File Format

```markdown
---
name: review-pr
description: Review a pull request for quality and correctness
trigger: /review-pr
model: claude
---

Review the PR at {{args}}. Check for:
- Logic errors
- Security issues
- Code style
- Test coverage
```

### Template Engine

Skills use **Tera** (`tera = "1"`) for template rendering. Available variables:

| Variable | Description |
|---|---|
| `{{args}}` | Raw CLI arguments string |
| `{{memory.user}}` | Contents of `~/.agent007/memory/user.md` |
| `{{memory.project}}` | Contents of `~/.agent007/memory/project.md` |
| `{{rag_context}}` | Top-k RAG results retrieved for this skill invocation |
| `{{date}}` | Current date (ISO 8601) |

Skills cannot call other skills in v1.

### Skill Location

```
~/.agent007/skills/
├── commit.md
├── review-pr.md
├── debug.md
└── custom-skill.md
```

### CLI Usage

```bash
agent007 skill add review-pr
agent007 /review-pr https://github.com/org/repo/pull/42
```

## IDE Integration (ide-bridge crate)

agent007 runs a local **`async-lsp`**-based JSON-RPC server. `async-lsp` is the actively maintained LSP framework used by production Rust tooling (e.g., rust-analyzer ecosystem). `tower-lsp` is not used due to maintenance concerns.

`async-lsp` is primarily designed around stdio transport. Dual-mode operation (stdio for Zed, TCP for VSCode/JetBrains) is implemented as follows:
- **Stdio mode:** `async-lsp` runs directly over stdin/stdout. Used for Zed (WASM sandbox constraint).
- **TCP mode:** A `tokio::net::TcpListener` accepts connections on port 7007 and bridges each connection into an `async-lsp` instance via `tokio::io::split`. VSCode and JetBrains use this mode.

Both modes share the same LSP handler logic — only the transport layer differs.

```
Zed Extension      ──── JSON-RPC / stdio ────► agent007 ide-bridge
VSCode Extension   ──── JSON-RPC / TCP  ────► agent007 ide-bridge
JetBrains Plugin   ──── JSON-RPC / TCP  ────► agent007 ide-bridge
                                                      │
                                                      ▼
                                               core agent engine
```

### Zed Integration

Zed WASM extensions run in a sandboxed environment with no direct network or filesystem access. The Zed extension communicates with agent007 via **stdio** (not TCP), using Zed's allowed host APIs for subprocess communication. The `ide-bridge` crate provides both a TCP mode (VSCode/JetBrains) and a stdio mode (Zed).

- Skills exposed as Zed slash commands
- Agent status in Zed status bar
- Inline completions via agent007 model router

### VSCode Integration

- Standard VSCode extension (TypeScript), connects via TCP JSON-RPC to local port 7007
- Command palette commands
- Status bar indicator

### JetBrains Integration

- Plugin via IntelliJ Platform SDK, connects via TCP JSON-RPC to local port 7007
- Action menu commands
- Tool window for agent status

## Self-Learning System (learning crate)

Inspired by Microsoft Agent Lightning. agent007 observes its own outcomes, scores them, and uses those signals to automatically improve its prompts and strategies over time — without manual rewriting.

### Phase 1 — RL-Style Reward Signals

#### Feedback Collector

Subscribes to the `Dispatcher` event bus and records every agent action and its outcome:

```rust
pub struct FeedbackEntry {
    pub id: Uuid,
    pub agent_id: AgentId,
    pub prompt_ref: PromptRef,
    pub skill_name: Option<String>,
    pub model: String,
    pub outcome: Outcome,
    pub reward: Option<f32>,          // set after scoring
    pub timestamp: DateTime<Utc>,
}

pub enum Outcome {
    Success,
    Failure { reason: String },
    UserRating { score: f32 },        // explicit thumbs up/down in TUI
    ToolError { tool: String },
}
```

Feedback entries are persisted to the Learning Store (separate table in LanceDB from the RAG index).

#### Reward Scorer

Assigns a scalar reward `f32` in `[-1.0, 1.0]` to each feedback entry using a combination of signals:

All signals contribute a signed value so the total reward is bounded in `[-1.0, 1.0]`:

| Signal | Weight | Value range | Signed contribution |
|---|---|---|---|
| Task completion | 0.4 | `+1.0` success / `-1.0` failure | `±1.0 × 0.4` → `[-0.4, +0.4]` |
| User rating | 0.3 | `+1.0` thumbs up / `-1.0` thumbs down | `±1.0 × 0.3` → `[-0.3, +0.3]` |
| Tool error rate | 0.2 | penalty: `-(error_count / total_calls)` | `[-0.2, 0.0]` |
| Follow-up retries | 0.1 | penalty: `-(retry_count / max_retries).min(1.0)` | `[-0.1, 0.0]` |

Total reward ∈ `[-1.0, +0.7]` when no user rating is provided; `[-1.0, +1.0]` with rating. Signals with no data for a session are omitted and the remaining weights are renormalized.

Weights are configurable in `config.toml`.

#### Prompt Optimizer

Runs after a configurable number of feedback entries accumulate (default: 10). For each skill or prompt pattern with a low average reward (below threshold, default `0.3`):

1. Retrieves the original prompt from the Skills store
2. Retrieves the top-k similar failed feedback entries from LanceDB (via RAG)
3. Calls the configured `reasoning` model (Claude by default) with a meta-prompt:

```
You are a prompt engineer. The following skill prompt has been producing
poor results (average reward: {{avg_reward}}). Here are examples of its
failures:

{{failure_examples}}

Rewrite the prompt to fix these failure patterns. Keep the same goal.
Return only the improved prompt text.
```

4. Stores the improved prompt as a new version in the Skills store (original is preserved)
5. Emits a `LearningEvent` on a **separate** dispatcher owned by the `learning` crate so the TUI can show it — avoiding a circular dependency with `core`

```rust
// In learning crate — its own event type and its own LocalDispatcher instance
pub enum LearningEvent {
    PromptImproved { skill_name: String, old_reward: f32, new_reward: f32 },
    FeedbackRecorded { agent_id: AgentId, reward: f32 },
    OptimizerTriggered { skill_name: String },
}
```

The `learning` crate depends on `core` (subscribes to `AgentEvent` via the core `Dispatcher`). `core` does **not** depend on `learning`. The TUI subscribes to both `core`'s `Dispatcher` and `learning`'s `LearningDispatcher` independently — no circular imports.

#### Learning Store

Separate namespace in LanceDB from the RAG index:

```
learning_store/
├── feedback/     # FeedbackEntry records with reward scores
└── versions/     # prompt versions per skill, with reward history
```

#### Config

```toml
[learning]
enabled = true
optimizer_threshold = 0.3        # avg reward below this triggers optimization
optimizer_trigger_count = 10     # feedback entries before optimizer runs
optimizer_model = "claude"       # model used to rewrite prompts
reward_weights.completion = 0.4
reward_weights.user_rating = 0.3
reward_weights.tool_errors = 0.2
reward_weights.retries = 0.1
```

### Phase 3 — Full RL Fine-Tuning (Ollama Local Models Only)

Claude and Codex APIs do not support fine-tuning. Full RL fine-tuning applies **only to local Ollama models** (llama3, mistral, gemma, etc.).

#### How it works

Ollama itself has no training capability — `ollama create` packages existing weights, it does not run gradient updates. The full RL fine-tuning pipeline uses an **external training tool** (run as a subprocess by agent007) to do actual weight updates, then packages the result back into Ollama.

1. **Trajectory collection** — the Feedback Collector accumulates full (prompt → response → reward) trajectories as JSONL records
2. **Export** — when the trajectory buffer is full, agent007 exports the JSONL to a temp directory in the format expected by the configured training tool
3. **External fine-tuning** — agent007 shells out to an external tool (user-configured: `llama.cpp finetune`, `unsloth`, or `axolotl`) which runs gradient updates on the base model weights and outputs a new GGUF file. This step requires a GPU and runs outside the Rust process.
4. **Packaging** — `ollama create agent007-<model>-v<N> --file <path-to-gguf>` registers the new GGUF with Ollama
5. **Model versioning** — each fine-tuned model is a new named Ollama model (`agent007-llama3-v2`, etc.) — the original is never overwritten
6. **A/B evaluation** — the new model version is tested against a held-out set of tasks before it replaces the current default

#### Phase 3 data flow

```
Feedback Collector
    │ trajectories (prompt, response, reward) as JSONL
    ▼
Trajectory Buffer (in LanceDB)
    │ when buffer full (configurable)
    ▼
JSONL Exporter
    │ writes training data to disk
    ▼
External Training Tool (subprocess)
    │ llama.cpp finetune / unsloth / axolotl
    │ (GPU required, runs outside Rust process)
    │ outputs updated GGUF weights
    ▼
ollama create agent007-<model>-v<N> --file <gguf>
    │
    ▼
A/B Evaluator
    │ passes? → promote to default in model router
    │ fails?  → discard GGUF, keep current
    ▼
OllamaProvider updated to new model version
```

#### Phase 3 config additions

```toml

ab_eval_pass_threshold = 0.6           # new model must beat current by 0.6 avg reward
```

### Code Zone Protection (zones crate)

Marks files and directories as protected regions. Every agent file operation (read, write, delete) is checked against zone rules before execution. Violations are blocked and logged.

#### Zone Levels

| Level | Agents can read | Agents can write | Stored in memory/RAG | Audit log entry |
|---|---|---|---|---|
| `unrestricted` | ✓ | ✓ | ✓ (default) | ✓ |
| `readonly` | ✓ | ✗ | ✓ | ✓ |
| `sensitive` | ✓ | ✗ | ✗ (never stored in memory or RAG index) | ✓ (access recorded, content omitted) |
| `forbidden` | ✗ | ✗ | ✗ | ✓ (violation recorded) |

All zone access is always recorded in the audit log — the distinction is whether the file *content* is stored in memory/RAG. `sensitive` files are audited but their content is never written to LanceDB or the markdown memory store.

#### Config

```toml
[zones]
forbidden  = ["secrets/", "keys/", ".env", "*.pem"]
readonly   = ["src/auth/", "src/payment/"]
sensitive  = ["src/crypto/"]
unrestricted = ["src/", "tests/", "docs/"]   # explicit (default for unmatched)
```

#### Enforcement Point

Zone rules are enforced in **`core`'s Tool Executor** — not in individual agents or sub-orchestrators. Every file read/write/delete passes through the Tool Executor's zone check before execution. This single enforcement point ensures no code path can bypass zone rules.

```rust
// In core — Tool Executor checks zones before every file operation
impl ToolExecutor {
    pub fn check_zone(&self, path: &Path, op: FileOp) -> Result<(), ZoneViolation>;
    // Called internally before every read/write/delete
}
```

#### Zone Rule Merging (Sub-Orchestrators)

Sub-orchestrators can declare additional zone rules scoped to their owned paths. Merging is **additive and monotone** — stricter always wins:

| Rule source | Wins over |
|---|---|
| Global `[zones]` config | Always applied everywhere |
| Sub-orchestrator `[zones]` | Applied within the sub-orchestrator's `scope` |
| Conflict resolution | Most restrictive level wins (`forbidden > sensitive > readonly > unrestricted`) |

A sub-orchestrator **cannot** loosen a global rule. If the global config marks `secrets/` as `forbidden`, a sub-orchestrator cannot override it to `readonly`. Merging algorithm: for each path, collect all matching rules from all sources and take the maximum restriction level.

#### Audit Log

Every agent action appended to `~/.agent007/audit/audit.log`:

```json
{"ts":"2026-03-16T10:00:00Z","agent":"WorkerAgent","action":"read","path":"src/auth/login.rs","zone":"readonly","allowed":true}
{"ts":"2026-03-16T10:00:01Z","agent":"WorkerAgent","action":"write","path":"src/auth/login.rs","zone":"readonly","allowed":false,"blocked":true}
```

Queryable via CLI:
```bash
agent007 audit --last 24h
agent007 audit --agent SecurityReviewer --blocked
agent007 audit --path "src/auth/**"
```

### Custom Workflow DSL (workflows crate)

TOML-defined multi-agent pipelines. Each workflow is a DAG of steps with typed inputs/outputs, model overrides, and optional human-in-the-loop gates.

#### Workflow File Format

**Output reference syntax:** Each step declares its output artifact with `output = "name"`. Downstream steps reference it by that name in their `inputs` array — always as a bare name, never as `step.output`. If a step produces no named output, it has no `output` key and cannot be referenced as an input.

**DAG concurrency model:** Steps are executed in dependency order. Two or more steps with no shared input/output dependency run concurrently by default — the runtime resolves the full dependency graph and executes all unblocked steps in parallel (up to `core.max_agents`). To force sequential execution of independent steps, add an explicit `depends_on = ["step_id"]`.

```toml
# ~/.agent007/workflows/tdd-feature.toml
name = "TDD Feature Development"
description = "Research → Architect → TestDesigner → Coder loop"

[[steps]]
id = "research"
agent = "Researcher"
model = "claude"
prompt = "Research best practices and existing patterns for: {{task}}"
output = "research_notes"
# no inputs → runs first, no dependencies

[[steps]]
id = "architect"
agent = "Architect"
model = "claude"
inputs = ["research_notes"]       # depends on research step
prompt = "Design an implementation plan based on the research"
output = "plan"
requires_approval = true          # pauses for human review before continuing

[[steps]]
id = "tests"
agent = "TestDesigner"
model = "codex"
inputs = ["plan"]                 # depends on architect step
prompt = "Write failing tests for the plan"
output = "test_code"
# runs concurrently with any other plan-dependent steps if any

[[steps]]
id = "implement"
agent = "Coder"
model = "codex"
inputs = ["plan", "test_code"]    # depends on both architect + tests steps
prompt = "Implement until all tests pass"
output = "implementation"

[[steps]]
id = "review"
agent = "SecurityReviewer"
model = "claude"
inputs = ["implementation"]       # depends on implement step (bare name, not "implement.output")
prompt = "Review for security vulnerabilities and correctness"
requires_approval = true

# Example: depends_on forces sequential ordering independent of inputs.
# Use when you want a step to wait for another step that produces no named output artifact.
# depends_on only controls execution order; it does NOT inject any output artifact.
# [[steps]]
# id = "notify"
# depends_on = ["review"]         # wait for review to complete, even though no inputs from it
# agent = "DocumentationWriter"
# prompt = "Update CHANGELOG with the reviewed changes"
```

#### Human-in-the-Loop Gates

When `requires_approval = true`, the workflow pauses and presents the current step's output in the TUI/CLI:

```
[APPROVAL REQUIRED]
Step: architect — Architect Agent output:
───────────────────────────────────────
Plan: Add JWT middleware to /api/v1/auth...
───────────────────────────────────────
Approve? [y/n/edit]
```

#### PersonaSpec Type and Registry

**Dependency isolation:** `personas` is a Phase 2 crate, but `core` is Phase 1. To keep Phase 1 buildable without `personas`, `core` defines a `PersonaProvider` trait. `personas` implements it. `cli` wires them at startup by wrapping `PersonaRegistry` in `Arc<dyn PersonaProvider>` and passing it to `Orchestrator`.

```rust
// In core crate (Phase 1) — trait definition only
pub struct PersonaSpec {
    pub name: String,
    pub description: String,
    pub system_prompt: String,
    pub preferred_model: String,       // "claude" | "codex" | "ollama"
    pub allowed_tools: Vec<String>,    // e.g., ["bash", "file_read", "web_search"]
}

pub trait PersonaProvider: Send + Sync {
    fn get(&self, name: &str) -> Option<PersonaSpec>;
    fn list(&self) -> Vec<PersonaSpec>;
}

// Phase 1 default — Orchestrator works without personas crate
pub struct NoOpPersonaProvider;
impl PersonaProvider for NoOpPersonaProvider {
    fn get(&self, _name: &str) -> Option<PersonaSpec> { None }
    fn list(&self) -> Vec<PersonaSpec> { vec![] }
}
```

```rust
// In personas crate (Phase 2) — concrete implementation
pub struct PersonaRegistry {
    personas: HashMap<String, PersonaSpec>,
}

#[derive(thiserror::Error, Debug)]
pub enum PersonaError {
    #[error("IO error reading persona dir: {0}")]
    Io(#[from] std::io::Error),
    #[error("failed to parse persona file {path}: {reason}")]
    ParseError { path: PathBuf, reason: String },
}

impl PersonaRegistry {
    /// Load built-in personas + any user overrides from `~/.agent007/personas/`
    pub fn load(user_dir: &Path) -> Result<Self, PersonaError>;
}

impl PersonaProvider for PersonaRegistry {
    fn get(&self, name: &str) -> Option<PersonaSpec> { ... }
    fn list(&self) -> Vec<PersonaSpec> { ... }
}
```

**Wiring in `cli`:** In Phase 1 the `cli` passes `Arc::new(NoOpPersonaProvider)` to `Orchestrator`. In Phase 2, `cli` loads `PersonaRegistry` and passes `Arc::new(registry)`. `core` never imports `personas` — the `Orchestrator` holds `Arc<dyn PersonaProvider>`.

Dependency direction: `core` defines the `PersonaProvider` trait and `PersonaSpec` struct. `personas` depends on `core` (to implement the trait). `core` never depends on `personas`. `cli` depends on both.

#### Regression Tracking

TestRunner compares results against the previous run stored in memory. Any test that was passing and now fails is flagged as a regression — highest priority fix.

#### TestRunner: Invocation and Output Parsing

The `TestRunner` agent invokes tests via **`cargo nextest`** (faster, better output structure than `cargo test`):

```bash
# Test execution with structured JSON output
cargo nextest run --message-format json 2>&1

# Coverage via cargo-llvm-cov (installed as a cargo extension)
cargo llvm-cov nextest --json 2>&1
```

`TestRunner` parses the nextest JSON event stream to populate `FailureReport`:
- `TestEvent::TestFinished { result: TestResult::Fail { .. } }` → failure entry
- `TestEvent::TestFinished { result: TestResult::Pass }` → pass counter
- `llvm-cov` JSON `data[0].totals` → `lines.percent` and `branches.percent`

Regression detection: `TestRunner` loads the previous run's result from the memory store (keyed by `run_id` of last run), compares test names, and flags any test that was `Pass` before and is `Fail` now.

If `cargo nextest` is not installed, `TestRunner` emits a `WorkflowError::MissingTool` error and halts with instructions to install it (`cargo install cargo-nextest`). There is no fallback — `cargo test`'s machine-readable output format is nightly-only and not suitable for production use. `cargo-nextest` is a hard dependency of the `testing` crate.

#### Config

```toml
[testing]
strategy_model = "claude"
writer_model = "codex"
test_runner = "cargo nextest"            # only supported value; hard dependency
coverage_tool = "cargo llvm-cov"         # "cargo llvm-cov" (default) | "none"
coverage_target = 80
report_format = "markdown"               # "markdown" | "json" | "junit"
auto_fix_on_failure = true
max_fix_iterations = 3
store_reports_in_memory = true           # regression tracking
```

### Simulation Agent Pipeline (simulation crate)

Domain-aware simulation pipeline that researches real-world parameters, generates synthetic inputs, runs the system under test, and validates outputs.

#### Pipeline Architecture

```
User defines scenario (TOML template)
        │
        ▼
┌───────────────┐
│  Researcher   │  searches: IEEE specs, RFCs, academic papers for domain params
│    Agent      │  outputs: validated parameter ranges, edge case distributions
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  ScenarioGen  │  inputs: domain params + user config
│    Agent      │  outputs: synthetic input datasets (CSV/JSON)
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Simulator    │  runs inputs through the system under test
│    Agent      │  outputs: raw results
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Validator    │  compares results against expected behavior + previous runs
│    Agent      │  outputs: pass/fail + anomaly report + regression flags
└───────┬───────┘
        │
        ▼
┌───────────────┐
│  Reporter     │  structured report stored in memory (enables regression detection)
└───────────────┘
```

#### Built-in Simulation Templates

Two templates ship in the repo as examples. Users can add any number in `~/.agent007/simulations/custom/`.

#### System Under Test Integration

Every simulation template declares a `[system_under_test]` section that tells the `Simulator` agent how to invoke the software being tested. The `Simulator` writes generated inputs to `{{scenario_file}}`, executes the command, reads results from `{{output_file}}`, and passes them to the `Validator`.

```toml
[system_under_test]
command = "./target/debug/my-wifi-ranging-tool"     # binary to invoke
args = ["--input", "{{scenario_file}}", "--output", "{{output_file}}"]
timeout_secs = 30                                    # per-scenario timeout
working_dir = "."                                    # relative to project root
env = { RUST_LOG = "warn" }                         # optional env vars
```

`{{scenario_file}}` and `{{output_file}}` are Tera variables resolved at runtime by the `Simulator` agent — it writes a temp CSV/JSON input file and passes its path via args. If the command exits non-zero, the scenario is marked as failed.

## Custom Agents and Hierarchical Sub-Orchestrators (custom-agents crate)

Users can define their own named agents — including **sub-orchestrators** that own a specific module, spawn their own worker agents for that domain, and report results back to the parent orchestrator.

### The Problem This Solves

A top-level orchestrator working on a large codebase shouldn't need to know the internals of every module. Instead, each complex module gets its own **sub-orchestrator** that:
- Owns a scoped view of the codebase (e.g., only `src/networking/libp2p/`)
- Understands the module's architecture, design docs, and test patterns via RAG
- Spawns generic worker agents (Coder, Tester, Reviewer) for subtasks within its scope
- Reports structured results back to its parent

### Hierarchy Model

```
Top-Level Orchestrator
│  task: "add mDNS peer discovery"
│
├──► LibP2PSubOrchestrator      (owns src/networking/libp2p/)
│       │  decomposes task into subtasks
│       ├──► Researcher          "research libp2p mDNS API"
│       ├──► Architect           "design the integration"
│       ├──► Coder               "implement discovery module"
│       ├──► TestDesigner        "write tests for discovery"
│       └──► CodeReviewer        "review the implementation"
│       │
│       └──► TaskResult → parent orchestrator
│
└──► NetworkingSubOrchestrator  (owns src/networking/ excluding libp2p/)
        │  parallel independent subtask
        ...
```

### Defining a Custom Agent (TOML)

```toml
# ~/.agent007/agents/libp2p-agent.toml
name = "LibP2PSubOrchestrator"
type = "sub-orchestrator"           # "worker" | "sub-orchestrator"
description = "Owns the libp2p networking module — decomposes tasks and manages its own workers"

# Module ownership — this agent's RAG context is scoped to these paths
scope = ["src/networking/libp2p/", "tests/networking/libp2p/"]

# Zone rules specific to this agent (merged with global zone config)
[zones]
readonly = ["src/networking/libp2p/core/"]    # core internals are read-only even to this agent

# System prompt — defines this agent's personality and expertise
system_prompt = """
You are the LibP2P module owner. You deeply understand the libp2p Rust library,
gossipsub, mDNS, QUIC transports, and peer discovery patterns.
You decompose tasks into subtasks and delegate to specialist agents.
You ensure all changes in your module are well-tested and reviewed before reporting back.
"""

# Which persona agents this sub-orchestrator can spawn
allowed_workers = ["Researcher", "Architect", "Coder", "TestDesigner", "CodeReviewer"]

# Preferred models for this agent's own reasoning
model = "claude"

# Memory scope — this agent has its own memory namespace
memory_namespace = "libp2p"
```

### Worker Agent Definition

```toml
# ~/.agent007/agents/rust-embedded-coder.toml
name = "RustEmbeddedCoder"
type = "worker"
description = "Specialist in no_std Rust for embedded targets"

system_prompt = """
You are an expert in no_std Rust for embedded systems.
You prioritize: minimal allocations, const generics, safe abstractions over unsafe blocks.
You never use std::collections — only heapless or fixed-size structures.
"""

model = "codex"
scope = ["src/embedded/", "src/hal/"]
```

### Agent Tree at Runtime

```
agent007 run "add mDNS discovery to the networking layer"
    │
    ▼ top-level orchestrator decomposes
    │
    ├─ task A: "libp2p mDNS" → dispatched to LibP2PSubOrchestrator
    │       └─ spawns: Researcher, Architect, Coder, TestDesigner
    │       └─ reports: TaskResult { output, files_changed, tests_passed }
    │
    └─ task B: "update routing table" → dispatched to NetworkingSubOrchestrator
            └─ parallel execution
```

### CLI

```bash
agent007 agent create --name "MyModuleAgent" --type sub-orchestrator
agent007 agent list
agent007 agent run LibP2PSubOrchestrator "add QUIC transport support"
agent007 agent inspect LibP2PSubOrchestrator    # show scope, memory, recent tasks
```

### Key Properties

- **Scope isolation** — each sub-orchestrator's RAG context is scoped to its owned paths. It cannot accidentally read unrelated modules.
- **Zone inheritance** — global zone rules apply everywhere; sub-orchestrators can add *stricter* rules for their scope, never looser ones.
- **Memory namespacing** — each sub-orchestrator has its own memory namespace (`libp2p`, `auth`, etc.) so learning and context don't bleed across modules. The namespace is a key prefix in the LanceDB table and the markdown memory store path (`~/.agent007/memory/<namespace>/`). The `memory` crate's `MemoryStore` exposes a `scoped(namespace: &str) -> ScopedMemoryStore` method that prefixes all reads/writes. The top-level RAG index remains global; namespace isolation is enforced at the read/write level, not at the index level.
- **Result reporting** — sub-orchestrators return a structured `SubTaskResult` including: output, files changed, tests written/passing, coverage delta, and any unresolved blockers.
- **Recursive depth** — sub-orchestrators can spawn other sub-orchestrators (e.g., a `NetworkingSubOrchestrator` that spawns `LibP2PSubOrchestrator` and `MQTTSubOrchestrator`). Maximum depth is configurable.

```toml
[core]
max_orchestrator_depth = 3    # prevents infinite nesting
```

## Phased Delivery

### Phase 1 — Core Foundation
- Cargo workspace setup (`crates/cli/` binary)
- `core` crate: agent engine, orchestrator, event bus, `Dispatcher` trait, CancellationToken shutdown
- `models` crate: Claude + Codex + Ollama providers + router + MockProvider
- `memory` crate: markdown store + LanceDB RAG
- `skills` crate: loader + Tera executor
- `hooks` crate: event hooks
- `mcp` crate: official Rust MCP SDK wrapper
- `learning` crate: feedback collector, reward scorer, prompt optimizer (RL-style signals)
- `tui` crate: ratatui dashboard (agents, tasks, models, learning panel)
- `cli` crate: wires everything together

### Phase 2 — Extended Feature Set
- `zones` crate: code zone protection + audit log
- `workflows` crate: custom workflow DSL + human-in-the-loop + budget guard
- `personas` crate: built-in agent persona library
- `git-agent` crate: git-aware ops, checkpoint/rollback, debug loop, impact analysis, session replay
- `custom-agents` crate: user-defined agents + hierarchical sub-orchestrators (see Custom Agents section)
- `testing` crate: full testing agent pipeline
- `simulation` crate: simulation pipeline + built-in WiFi RTT + WiFi roaming templates
- `ide-bridge` crate: async-lsp server (TCP + stdio modes)
- Zed extension (WASM, stdio)
- VSCode extension (TypeScript, TCP)
- JetBrains plugin (TCP)
- `web` crate: axum server + browser dashboard

### Phase 3 — Distribution + Full RL Fine-Tuning
- Agent nodes as separate binaries
- `Dispatcher` trait network transport (libp2p via zswarm, or gRPC)
- Qdrant as distributed vector DB
- Cluster orchestration
- `learning` crate: full RL fine-tuning (trajectory buffer, external training tool, GGUF, ollama create, A/B eval)
